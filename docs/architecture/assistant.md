# AI Dashboard Assistant

Detailed reference for the dashboard assistant (`internal/core/assistant` + `internal/app/ai` + `cmd/ai`). Linked from the root [`CLAUDE.md`](../../CLAUDE.md) — read this when working on the assistant's turn pipeline, tools, repair loop, or deployment. Ported from the retired TypeScript service (`es/pug-sh/ai`).

The service implements `ai.dashboards.v1.DashboardAssistantService.Turn` (server-streaming): one user message against a client-owned dashboard draft in; streamed assistant prose plus validated `TileOp`s out, in the deterministic chunk order **text → ops → done** (tools cannot yield mid-stream; the op sink drains only after the model stream completes). Ops, never whole-draft rewrites: `DashboardsService.Upsert` deletes tiles absent from its request, so an operation contract is what makes silence unable to delete. The client owns the draft and its reducer; the webapp commits via `Upsert`. Markdown tiles are not authored — insight tiles only.

**Topology.** `cmd/ai` (default port `PUG_AI_PORT`=8001) has exactly three external dependencies: the model provider named by `MODEL_AGENT` (anthropic / openai / openai-compatible — endpoint and API key env are part of the route; see **Model routing**), Redis (history + traces, via `REDIS_URL`), and the main pug API (`PUG_API_BASE_URL`) reached through an `insightsv1connect` client with per-call forwarded `Authorization` + `x-project-id` headers. No Postgres, no ClickHouse, no NATS. Misconfiguration fails at boot (crash-loop loudly); there is no idle mode — an ai Deployment exists only to serve. Exposed three ways: `pug ai`, a `MODEL_AGENT`-gated component of `pug dev` (`ai.DevStatus`), and the `pug-ai` per-role image (release matrix row `{name: ai, cmd: ai, target: app}`).

**Auth.** `WithAssistantAuth` is a local JWT **spend gate**, not the security boundary: the DB-free core of the server's `WithJWTAuth` (bearer + HS256 + `coreauth.Issuer`/`Audience` + required expiry, needs `PUG_JWT_SECRET_KEY`) plus a required `x-project-id`. It rejects junk before model spend — a turn with no tool calls would otherwise never be rejected — while a revoked-but-unexpired token still passes locally and is enforced by the insights callback, which re-runs full auth (including org membership for the named project) on every tool call. The service holds no credentials of its own; a viewer cannot escalate through the assistant. The ai mux is deliberately **outside** the server's authz registry/contract tests (those cover only the server's mux), mirroring how `/mcp` owns its own boundary. The caller's JWT is never logged and never stored in a trace (`TurnTrace` has no credential field, pinned by a test). Tool inputs and outputs — tile payloads included — *are* in the trace: that is what makes it a debug trace, and it is no more sensitive than the `message`/`reply` already beside it.

**Turn pipeline** (`Service.Turn`): apply the turn deadline (`turnTimeout`, 5m — a stream has none of its own, and `maxSteps` rounds of 60s insight calls compose to far longer than any real turn; `DeadlineExceeded`/`Canceled` map to their own Connect codes so an abandoned stream is not logged as a server fault) → reject an incomplete caller scope (`ErrIncompleteScope`) → take the conversation's turn lock (`SET NX` with the turn's TTL; a concurrent turn on the same id — another tab, a client retry mid-stream — is `ErrTurnInProgress` → `CodeAborted`, since history is a plain GET/SET and two interleaved turns would drop one exchange) → load history (Redis outage → `CodeUnavailable` "conversation storage unavailable (load)" — **fail closed**; silently serving empty history reads as "the model forgot everything") → build per-turn tools → `aisdk.StreamText` with messages `[draft summary, …history, user message]`, `WithStopWhen(StepCountIs(12))` (the SDK default is ONE step), text deltas emitted as they arrive → partition the op sink → append user+assistant messages, save history trimmed to `historyByteBudget` (64 KiB of content, oldest dropped — an uncapped history eventually outgrows the context window and fails every later turn; fail closed, "(save)") → best-effort debug trace (log + `telemetry.RecordError`, never fails the turn) → **then** emit the ops. Ops go last because an op the client has applied is a durable draft change, so a save failure has to precede it; the trace is written before them so the one turn that diverges — history committed, emission failed — is the one that leaves a record.

**Tools.** Three insight reads (`get_insights_filter_schema`, `get_insights_property_values`, `query_insights`) over the shared Connect API — each reply capped at `maxToolResultBytes` (32 KiB, truncation marker tells the model to narrow the query), since it rides every later step and the debug trace — and three ops (`add_tile`, `update_tile`, `remove_tile`). Tool failures are returned to the model as `ERROR: …` strings, never as Go errors — the grafana SDK wouldn't abort the turn on an Execute error (unlike the TS SDK this ports), but string returns keep the model-visible format identical to the TS service and out of the SDK's error-result wrapping. That string is the *repair* channel only: `safely` also logs, splitting on the Connect code (`modelRepairable`) so the model's own mistakes stay at warn while an upstream failure is an error + `telemetry.RecordError` — otherwise an insights outage would be invisible to operators. `remove_tile` is the one destructive op and the only one that checks its id against the draft; a tile added earlier in the same turn has no id until `Upsert` assigns one, so the draft is the whole universe of removable ids.

**Shape grounding** (`shape.go`). The system prompt carries the tile's JSON Schema plus its cross-field rules, both rendered from the generated types at init — one copy in the prompt rather than three in the tool descriptions, since `add_tile`, `update_tile` and `query_insights` all need the same spec shape. Without it the model has a worked *trends* example and nothing else: the `top_k`, `user_flow`, `map` and `session` field layouts are unstated, so it invents them and discovers the shape through the repair loop. The schema is `properties.tiles.items` lifted out of the generated `dashboardsv1mcp` Upsert tool schema (the package is otherwise unused — only insights/activity/profiles are linked into `/mcp`), so the per-field `pattern`/`maxLength`/enum-name constraints come from protovalidate for free. Two transforms make it match what we actually parse: `id` and `position` are dropped (`submit` assigns both and discards a model-supplied value), and the MCP `{"which","insight","markdown"}` discriminator is flattened to proto3 JSON's bare `insight` key — advertising the discriminator would teach a shape `tileFromJSON` rejects on every call. For the same reason `exampleTileJSON` renders with `UseProtoNames: true`; the generated schema is snake_case and the example must not disagree with it. The rules are the message- and field-level `(buf.validate).cel` messages walked from `DashboardTileInput`, deduped and sorted — the cross-field constraints ("conversion_window is only valid for funnel insight type", "session insights cannot also specify events") that JSON Schema structurally cannot express, and the same strings the repair loop hands back *after* the model has already broken one.

This is deliberately **not** wired as the tools' `InputSchema`. The SDK validates `InputSchema` before `Execute` and routes a failure through `rejectToolCall` (`streamtext.go`), which feeds the error to the model but **skips `Execute`** — so `attempts`, the `givenUp` latch and the op sink are all bypassed, and a tile that keeps failing the schema loops until `maxSteps` and then vanishes with no flagged op and no `TurnDone.failed` entry. That is exactly the silent no-op the repair budget exists to prevent. As prompt text every failure still lands in `Execute` and stays inside the budget; the schema informs, protovalidate enforces. Cost is ~13 KB (~10.2 KB shape + ~2.8 KB rules) on a stable prefix re-sent on every one of up to 12 steps, which is what `systemCacheOptions` pays for.

**Repair loop.** A submitted tile is decoded with `protojson` (real proto3 JSON — flat oneof member keys; unknown fields are parse failures) and validated with protovalidate-go against the same rules `Upsert` enforces. Violations are handed back to the model as the tool reply — that IS the repair loop. Budget: 3 attempts **per target** (`add:<intent>` / `update:<tile id>`, reset on success), shared across parse and validation failures; past budget the tile is emitted **flagged** (`TileOp.violations` non-empty — the client must block save; `Upsert` re-enforces server-side) — never silently dropped. A `givenUp` latch stops repeat emissions after the budget. `intent` carries `minLength: 1` in both tool schemas (the SDK validates a tool's `InputSchema` before `Execute`), so unlabelled tiles cannot collapse into one shared budget. A validator runtime error (`validator.error`) fails the tile outright into `TurnDone.failed`: fail-closed, an unvalidated tile is never emitted as if checked. Because flagged tiles are deliberately invalid protos, the ai server's validate interceptor must NEVER get `WithValidateResponses()` — and the request's `state.draft` is `ignore = IGNORE_ALWAYS` in the proto for the mirror reason: the draft holding a flagged tile is exactly the one the user sends back asking for a fix. Body size is bounded instead, the same `WithRequestLimits` + `WithReadMaxBytes` pair as the main server. `exampleTileJSON` (the worked example in the tool descriptions) is rendered from the generated types via protojson — a proto rename breaks the build, not a prompt string — and a self-check test asserts it validates, and that it matches the schema the prompt advertises.

**Prompt caching** (`systemCacheOptions`, `llm.go`). `runLoop` sends the system prompt via `WithSystemMessages` with an Anthropic `cache_control: ephemeral` breakpoint on it. Anthropic's cacheable prefix is ordered tools → system → messages and a breakpoint caches everything up to and including itself, so the one marker covers **both** the tool definitions and the whole system prompt — the entire static part of the request. That prefix is byte-identical across every step of a turn, every turn of a conversation, and every caller of the deployment, so it hits on steps 2..12 and again on the next turn within the 5m TTL; the shape and rules are what make it worth caching at all. Deliberately unconditional rather than provider-gated: `provider.ProviderOptions` is keyed by provider name, so openai and openai-compatible never read an `"anthropic"` entry (both cache a stable prefix server-side with no marker anyway), and the anthropic provider explicitly tolerates a bare `AnthropicCacheControl` where it looks for system-message options. Only the static prefix is marked — history is not, so a long conversation does not write a fresh cache entry per turn. `TestRunLoop_SystemPromptCarriesCacheBreakpoint` pins that the marker reaches the model call, since nothing downstream of the provider is observable from here.

**Placement** (`placement.go`): append-below — new tiles at x=0 under the lowest existing tile; the model's proposed w/h are honored and clamped (w≤72, h≤60), its x/y ignored, so overlap is unrepresentable. Always returns a complete position (the `grid_position.complete` CEL rule rejects partial ones). The cursor is turn-scoped: the client applies ops only after the turn, so tiles added earlier this turn are not in the draft and re-reading it would stack them all on one row. It advances only when a tile is emitted, so a repair retry does not burn a row. **`update_tile` keeps the edited tile's existing position** — an update changes what a tile shows, not where it sits. A tile stored without a position counts as sitting at the FE's `DEFAULT_POSITION` (0,0,36,18), for both the cursor and an update. `submit` also drops a model-supplied `id`: `Upsert` assigns them and rejects one it does not know. Both `update_tile` and `remove_tile` reject an id the draft does not hold: `Upsert` rejects a populated unmatched id (`ErrDashboardTileNotFound`), so emitting one would hand the client an op it could never save.

**Concurrency.** The SDK executes every tool call in a step on its own goroutine and makes goroutine safety the caller's problem (`openspec/specs/concurrent-tool-execution/spec.md` in the pinned `v0.1.0-alpha.1`), with no way to serialize. `buildOpTools` therefore guards all four pieces of turn state — `attempts`, `givenUp`, the placement cursor, and the op sink — under one mutex. Unguarded, two `add_tile` calls in one step race the maps (a fatal runtime error no `recover` catches, so `RecoverHandlerPanic` would not contain it) and lose ops to concurrent appends.

**Redis shapes.** Keys are scoped `<project_id>:<customer_id>:<conversation_id>` (`keyScope`): `conversation:<scope>:messages` = `[{"role":<enum int>,"content":"…"}]`, `conversation:<scope>:turn` = the turn lock (TTL = `turnTimeout`), `debug:<scope>` = RPUSH'd `TurnTrace` JSON (`projectId`, `message`, `reply`, `toolCalls[{toolName,input,output}]`, `ops`, `failed[{intent,violations}]`, `model`, `durationMs` — no JWT field by design). Both carry a 7-day TTL refreshed on write. `conversation_id` is client-minted, so the scope is the only thing keeping one caller's conversation out of another's reach; `Turn` fails closed on an incomplete scope (`ErrIncompleteScope` → `Unauthenticated`). The JWT-derived `customer_id` sits in the middle, so a forged project or conversation id cannot land on another caller's key — and both outer segments are charset-bounded anyway (`^[A-Za-z0-9_-]+$`; `conversation_id` ≤128 in the proto, `x-project-id` ≤64 in `WithAssistantAuth`). The **values** stay byte-compatible with the retired TS service; the **keys** deliberately are not, so its in-flight conversations do not carry over — 7-day working data, nothing to migrate.

**Model routing** (`llm.go`): `MODEL_AGENT=provider:model?opts`, parsed at boot. Providers: `anthropic` (`ANTHROPIC_API_KEY`), `openai` (`OPENAI_API_KEY`, Responses API), `openai-compatible` (`base_url` required; optional `api_key_env` names the key env — omit for local servers like Ollama). Sampling opts (`temperature`/`top_p`/`top_k`) become per-call options, **stripped for anthropic** (its current models 400 on them). The grafana ai-sdk (`v0.1.0-alpha.1`; provider submodules pinned by pseudo-version — they are untagged) is confined to `loop.go` + `llm.go`; everything else sees only `provider.LanguageModel` and the `CallOptions` named type, and tests drive the loop with `assistanttest.ScriptedModel`.

**Env contract:** `PUG_AI_PORT` (8001), `PUG_API_BASE_URL` (required), `PUG_JWT_SECRET_KEY` (required), `MODEL_AGENT` (required) + provider key env, `REDIS_URL` (required), `PUG_CORS_ORIGINS` (`*`) — same CORS var as the server; `pogrpc.WithCORS` already allows `Authorization` + `X-Project-Id`.

Tests: unit suite is `-short`-safe; history/trace/service/handler tests ride `testutil.SetupRedis` (package wires `testutil.Main`, no `t.Parallel`). The handler tests are the wire-contract round-trip: a real generated streaming client against the same `buildMux` production uses.
